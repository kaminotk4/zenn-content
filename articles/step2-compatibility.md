## はじめに

STEP1.5で細部を磨き終えた。ローディングアニメーション、エラーハンドリング、SEO対策——チェックリストを一つずつ潰していく作業は地味だが、リリース後の安心感が違う。

そしていよいよ本題だ。**月3,000円の収益化**という目標に向けて、核心機能となる**相性占い**の実装に着手する。

なぜ相性占いが核心なのか。単体の星座占いは無料サイトが山ほどある。差別化するなら「あなたと○○さんの相性は？」という問いに答える機能しかない。相性占いなら課金の動機が自然に生まれる。「好きな人との相性を知りたい」——そのために少し払う人は必ずいる。

## 相性スコアの設計

### 本格的な相性占い（シナストリー）を調べた

まず「ホロスコープ 相性 占い 方法」で調べると、**シナストリー**という手法が出てきた。2人のホロスコープを重ね合わせ、惑星同士のアスペクト（角度関係）を見る本格的な手法だ。

たとえば「Aさんの太陽とBさんの金星がトライン（120度）を形成している場合は相性良好」といった具合に、10惑星×10惑星=100通りのアスペクトを総合的に判断する。精度は高いが、実装に必要な情報も多い。

**シナストリーに必要なもの：**
- 生年月日
- 生まれた時刻（時・分）
- 生まれた場所（緯度・経度）

時刻と場所がないと正確なホロスコープが出せない。MVP段階で「生年月日・時刻・場所を入力してください」は離脱率が高くなる。

### 簡易版：エレメント相性ベースを採用

そこで、**生年月日のみで実装できる簡易版**として「エレメント相性」を採用した。

西洋占星術では12星座を4つのエレメント（元素）に分類する。

| エレメント | 星座 |
|---|---|
| 火（Fire） | 牡羊・獅子・射手 |
| 土（Earth） | 牡牛・乙女・山羊 |
| 風（Air） | 双子・天秤・水瓶 |
| 水（Water） | 蟹・蠍・魚 |

エレメント間の相性は伝統的に以下のように定義されている。

| 組み合わせ | 評価 |
|---|---|
| 同じエレメント | ◎（とても良い） |
| 火×風、土×水 | ○（良い） |
| 火×土、火×水、風×水、風×土 | △（普通） |
| 火×水、土×風（正反対） | ✕（課題あり） |

### スコア計算式

「生年月日から1つの星座を出して相性を見る」だけでは単純すぎる。**3天体**（太陽・月・金星）を使い、それぞれのエレメント相性を積み上げることにした。

```
◎ = 3点
○ = 2点
△ = 1点
✕ = 0点
```

3天体の合計は 0〜9点。これを**15〜100点**に正規化してスコアとして表示する。

```
正規化スコア = ((生点 / 9) × 85) + 15
```

15点スタートにしたのは「相性0点」という絶望的な表示を避けるため。占いなので、最低でも「少し縁がある」くらいのポジティブさを残したい。

### STEP3でのアップグレード計画

この簡易版はあくまでMVPだ。ユーザーが増えてきたら**STEP3でシナストリー本格版**にアップグレードする予定。

ステップを分けた理由：
1. 生年月日のみで入力ハードルを下げてユーザーを集める
2. 相性占いへの需要を確認してから本格実装に投資する
3. シナストリー実装は計算量が多く、バックエンドが必要になる可能性がある

## 定型文432パターンの作成

### なぜ432パターンなのか

12星座 × 12星座 × 3天体（太陽・月・金星） = **432パターン**。

各星座ペアに対して「太陽の相性コメント」「月の相性コメント」「金星の相性コメント」を用意する計算だ。

実際には「牡羊×牡羊」「牡羊×牡牛」……と全ペアを書き下ろすことになる。1パターン約200〜250文字で計算すると、総文字数は4〜6万字。一人で書ける量ではない。

### AI生成 vs 定型文を比較検討した

当初は「占い文章はAIにリアルタイム生成させればいい」と考えていた。しかし比較検討すると、課金機能との相性で**定型文に軍配が上がった**。

**AI生成のメリット・デメリット：**

| | AI生成 |
|---|---|
| ✅ | 毎回違う文章でユーザー飽きにくい |
| ✅ | パターン数の制約なし |
| ❌ | APIコストが発生（課金前のユーザーにも） |
| ❌ | レスポンス速度が遅い（3〜10秒） |
| ❌ | 品質にばらつきが出る |
| ❌ | プロンプト管理が複雑 |

**定型文のメリット・デメリット：**

| | 定型文 |
|---|---|
| ✅ | 初期コスト（一度作れば0円） |
| ✅ | 表示が即時 |
| ✅ | 品質を事前にコントロールできる |
| ✅ | 課金後の全文表示で「ちゃんとした文章」を保証できる |
| ❌ | 432パターン作成の初期工数 |
| ❌ | 同じ相性を何度見ても同じ文章 |

**課金要素は品質重視**という方針で定型文を選択した。無課金ユーザーには結果をぼかして見せ、課金後に全文を表示する。その「課金後の全文」が粗悪なAI生成文だと課金体験が悪い。定型文であれば品質を担保した上でリリースできる。

### Claude Codeで1星座ずつ生成

432パターンを一気に生成しようとすると、トークン上限に引っかかる。そこでClaude Codeに依頼する際は**1星座ずつ順番に生成**する作戦を取った。

作業の流れ：

```
1. 牡羊座が絡む全ペア（牡羊×牡羊〜牡羊×魚）を生成
   → 12ペア × 3コメント = 36パターン
2. 生成結果をJSONファイルに追記
3. 次の星座（牡牛座）へ
4. 12星座分繰り返す
```

プロンプトの工夫点：
- 各パターン200〜250文字、です・ます調
- 3部構成：①組み合わせの特徴 ②良い点 ③気をつける点・アドバイス
- 星座名を文中に自然に織り込む
- 1星座ずつ順番に追記する形で、トークン上限エラーを回避

### 全パターン揃っているか自動検証

生成が終わったら、Claude Codeに「12星座×3天体の全パターンが揃っているか確認してください」と指示した。不足キーがないことをその場で確認してもらえた。

432個の穴を埋めきったという事実が確認できた時の達成感は格別だった。

## 画面実装

### 相性入力フォーム

自分の生年月日は単体占いで既に入力済みのため、画面上部に「あなた：〇〇年〇月〇日生まれ」として表示する。入力するのは相手の生年月日のみ。フォームは「相手の生年月日を入力してください」という1つの入力欄と、「相性を占う」「戻る」の2ボタンだけだ。

UX上の工夫：
- 自分の情報は再入力不要で、相手だけ入力すればすぐ診断できる
- バリデーションは「未入力」のみ。複雑な検証は離脱を招く

### 結果画面：チラ見せ＋ぼかし演出

課金壁の演出にこだわった。

無課金状態では：
- スコア（数値）は表示する
- 太陽・月・金星すべての相性コメントの先頭25文字を表示し、26文字以降をぼかし処理
- 「詳細を見る（¥300）」ボタンで課金導線へ

```css
.blurred-content {
  filter: blur(4px);
  user-select: none;
  pointer-events: none;
  position: relative;
}

.blurred-content::after {
  content: '';
  position: absolute;
  inset: 0;
  background: linear-gradient(
    to bottom,
    transparent 0%,
    rgba(16, 14, 10, 0.55) 40%,
    #100e0a 85%
  );
}
```

```

グラデーションのぼかしは「気になるけど読めない」絶妙なラインを狙った。完全に隠すより、チラ見えの方が課金モチベーションが上がる。

妻に実際に触ってもらったところ、「2行目の途中で切れると先が気になって課金したくなる」というフィードバックをもらった。最初の「。」まで表示する方式から、先頭25文字はそのまま表示し26文字以降をぼかす方式に変更した。文章がブツ切りにならず、途中からじわっとぼやけていく演出になった。

### ソースコード閲覧対策

CSSのblurでぼかすだけでは、ブラウザの開発者ツールでHTMLを見ると全文が読めてしまう。

そこで未課金時は実際の文章をHTMLに出力せず、先頭25文字を繰り返したダミーテキストをぼかして表示する方式に変更した。

```html
<span style="filter: blur(5px);">
  天秤座の穏やかな調和志向と魚座の豊かな感受性が溶け
  天秤座の穏やかな調和志向と魚座の豊かな感受性が溶け
  ...（繰り返し）
</span>
```

開発者ツールで見ても実際の占い結果は見えない。¥300という低価格ではあるが、課金体験の誠実さとして対応した。

### テストモード実装

開発中は課金フローを毎回通せない。`localhost` アクセス時のみ全文を表示するテストモードを実装した。

```typescript
const isTestMode = window.location.hostname === 'localhost';
```

`localhost` 以外ではチラ見せ表示になるので、本番環境でテストモードが漏れる心配はない。

### sessionStorageでリロード対策

相性診断の結果はsessionStorageに保存した。

理由：ブラウザリロードや「戻る」操作でも結果を再計算せずに復元できる。

```typescript
// 結果ページ表示時
useEffect(() => {
  const savedResult = sessionStorage.getItem('compatibility_result');
  if (savedResult) {
    setResult(JSON.parse(savedResult));
  }
}, []);

// 診断実行時
sessionStorage.setItem('compatibility_result', JSON.stringify(result));
setScreen('compatibility-result');
```

### 総合まとめ文の追加

スコア直下に3天体を踏まえた総合まとめ文を表示する機能も追加した。

太陽・月・金星それぞれの組み合わせごとに40〜60文字の短文を用意し、3文を連続して表示する。星座名は使わず、前後の文と自然に繋がるよう表現を統一した。

パターン数は sun・moon・venus 各144パターン、合計432パターン。既存の詳細解説文とは別に、概要として読める文章として設計した。

## まとめ

### 設計の意思決定プロセスを記録することの大切さ

今回の記事を書きながら気づいたことがある。**なぜその設計にしたか**を言語化するのは、実装後すぐでないと難しい。

「AI生成じゃなく定型文を選んだ理由」「432パターンの数え方」「15点スタートの根拠」——実装している最中は自明に感じるが、数週間後には「なんでこうしたんだっけ」となる。

Zennに書いておけば、未来の自分へのメモになる。そして誰かの参考にもなるかもしれない。

### 「まず定型文、後でAIにアップグレード」の方針

今回採用したこの方針は、副業開発全般に使えると思っている。

- まず動くものを出す（定型文でOK）
- ユーザーの反応を見る
- 需要が確認できたら品質を上げる（AIへアップグレード）

いきなりAI連携の複雑な実装に挑むより、確実に動くMVPを出してフィードバックを得る方が効率的だ。
