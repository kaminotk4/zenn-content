## はじめに

「取締役エンジニアがClaude Codeで副業を始める実録」第9回です。

前回（[#8 Claude Codeで¥300課金を実装したら、Vercel Hobbyが商用利用禁止だった話](https://zenn.dev/kaminotk4/articles/stripe-payment-vercel-ng)）では、Stripe Checkoutによる課金実装を進めた直後に、ホスティング先のVercel Hobbyプランが商用利用禁止だと判明しました。固定費を増やしたくないため、Vercel Proへのアップグレードではなく他サービスへの移行を検討する、というところで終わりました。

今回はその後の話です。移行先の選定・Netlify移行作業・初回デプロイで白画面になったトラブルとその解決まで、立て直しの全工程を書きます。

また、移行と並行して課金再開の目安を「月400PV」と設定しました。なぜ400なのかは、後半のGA4導入のセクションで触れます。

## 移行先の選定：NetlifyかCloudflare Pagesか

「無料プランで商用利用が可能なホスティングサービス」で調べると、候補はすぐに2つに絞られました。

| サービス | 無料枠の商用利用 | 備考 |
|---|---|---|
| **Netlify** | ○ | 月300クレジット制。超過するとサイト停止 |
| **Cloudflare Pages** | ○ | 無制限に近い。エッジ配信で高速 |

スペックだけ見ればCloudflare Pagesの方が魅力的です。制限が緩く、パフォーマンスも高い。では、なぜNetlifyを選んだのか。

### Cloudflare Pagesを見送った理由

Cloudflare Pagesを本格的に使おうとすると、サーバーサイド処理は **Cloudflare Workers** を使うことになります。

Workers は独自の実行環境を持っており、Node.jsとは仕様が一部異なります。今回移植したいのはVercel Functionsで動いていたStripeの決済API（`api/create-checkout-session.ts`）です。そのままWorkers上で動くかどうかを検証するには、Workers特有の記法や制約を調べる必要があります。

スペックの差は確かに魅力的でしたが、月400PV規模なら実際にはほとんど気にならない範囲です。それより移行を早く終わらせられるかどうかの方が、今の自分には重要でした。

副業に使える時間は週5時間程度。その枠の中でWorkersの学習コストを払うのは、今の段階では割に合わないと判断しました。

Cloudflareは「将来PVが増えて無料枠の制限が問題になってきたら、そのときに改めて検討する」という選択肢として残しています。今は移行を早く終わらせて、PV計測フェーズに進む方が優先です。

### Netlifyを選んだ理由

Netlifyを選んだ理由は3つです。

**① 移行コストが低い**

Netlifyには Netlify Functions という仕組みがあり、`netlify/functions/` フォルダにファイルを置くとAPIエンドポイントが作れます。Vercel Functionsの`api/`フォルダと同じ発想です。ただ、今回はそれよりも単純な方法を取りました。後述しますが、Stripe実装の構成を変えたため、Netlify Functions自体を使わずに済みました。

**② 日本語の情報が多い**

困ったときに日本語で検索して答えが見つかるかどうかは、週5時間の副業では重要です。Netlifyは国内での採用実績が多く、トラブルシューティングの記事も豊富です。

**③ 決済まわりは後回しでよいと割り切れた**

移行を機にStripe実装も改めて確認しました。結論として、決済まわりをNetlify向けに完全に作り直すのは、課金を実際に有効化するタイミングに合わせてやればよいと判断しました。

現時点では月400PVに達するまで課金導線をオフにする方針です。決済ボタン自体を非表示にしているため、今すぐ決済フローを繋ぎ込む必要はありません。まず静的サイトとしてNetlifyに移せれば十分——そう割り切れたことで、移行作業そのものをシンプルに済ませることができました。決済まわりの本格的な作り込みは、課金再開のタイミングでまとめて行う宿題として残しています。

## Netlify移行作業：アカウント作成からデプロイまで

移行作業そのものは、拍子抜けするほど早く終わりました。

1. Netlifyのサイトでアカウントを作成
2. GitHubと連携し、対象リポジトリを選択
3. Netlifyがリポジトリを検出して、自動でサイトを作成

GitHubと連携した瞬間から「デプロイ済み」の状態になり、URLも発行されます。「え、もう終わり？」と思いました。Vercelのときと同じように、Claude Codeに任せると作業があっさり片付く。毎回のことながら、素直に感心します。

Vercelのときと操作感はほぼ同じです。乗り換えに心理的なハードルはありませんでした。

そして、発行されたURLをブラウザで開きました。

## トラブル：初回デプロイが白画面になった

画面が、真っ白でした。

エラーが出ているわけではありません。ページは開いています。ただ、何も表示されない。

デプロイのログを確認しに戻ると、ビルドは「成功」と表示されています。何が起きているのか、最初はまったくわかりませんでした。成功と表示されているのに画面が真っ白という状況が腑に落ちず、ログと画面を見比べながら戸惑うばかりでした。

### 原因：Build commandとPublish directoryが未設定

ブラウザの開発者ツール（F12）でコンソールを開くと、エラーが出ていました。

```
Failed to load module script: Expected a JavaScript module script but the server responded with a MIME type of "text/html".
```

「MIMEタイプ」というのは、ファイルの種類を表す識別子です。ブラウザがJavaScriptファイルを要求したのに、サーバーが「これはHTMLです」という種類のファイルを返してきた——その食い違いで、ブラウザがスクリプトの実行を拒否していました。

なぜこうなったのか。順を追って説明します。

このアプリはReact + Viteで作られています。**Vite** はフロントエンド開発のツールで、開発中はローカルで動かすための仮想サーバーを用意してくれます。本番環境に出すときは `npm run build` というコマンドを実行し、最適化されたファイル一式を `dist/` フォルダに出力します（これを「ビルド」と呼びます）。

Netlifyのデプロイで問題になったのは、この「ビルド」が走っていなかったことです。

Netlifyの管理画面でリポジトリを連携したとき、 **Build command** と **Publish directory** の設定が空白のままになっていました。

- **Build command**（ビルドコマンド）：デプロイ前に実行するコマンド。今回は `npm run build` を指定すべきでしたが、未設定でした。
- **Publish directory**（公開ディレクトリ）：ビルド後にNetlifyが配信するフォルダのパス。今回は `dist` を指定すべきでしたが、未設定でした。

設定が空白なので、Netlifyはビルドを実行せずにリポジトリのルートフォルダをそのまま配信しました。ルートには開発用の `index.html` がありますが、そこに書かれているJavaScriptの参照先（`/assets/xxx.js` のようなパス）は `dist/` フォルダの中を向いています。`dist/` は生成されていないので、ファイルが存在しません。ブラウザがJSファイルを取りに行くと、Netlifyは「そのパスのファイルはない、`index.html` を返しておきます」と応答します。結果、JSの場所にHTMLが来て、MIMEタイプの不一致が起きていた、というわけです。

「デプロイが成功している」のは、ファイルを配信すること自体には成功しているからです。配信しているものが意図したものではなかった、というのがこのトラブルの本質でした。

### 解決：netlify.toml を作成する

Netlifyでは、`netlify.toml` というファイルをリポジトリのルートに置くことで、ビルドの設定をコードとして管理できます。管理画面でポチポチ設定するよりも、ファイルで管理しておく方がリポジトリを見れば設定がわかるので再現性があります。

この `netlify.toml` も、Claude Code に依頼して作ってもらいました。

作成した `netlify.toml` の内容（この時点でのビルド設定部分）：

```toml
[build]
  command = "npm run build"
  publish = "dist"
```

`command` でビルドコマンドを指定し、`publish` でビルド後の出力先フォルダを指定しています。これをコミットしてpushすると、Netlifyが自動でデプロイを再実行しました。

今度はアプリが表示されました。安堵したのはもちろんですが、それ以上に、原因の分からないトラブルにも Claude Code が愚痴ひとつ言わず付き合ってくれたことがありがたかったです。嫌な空気にならずに解決まで導いてくれる——そういう存在だと、困ったときに頼りやすいと改めて感じました。

## SPAのリダイレクト設定：直接URLアクセスで404が出る問題

アプリの表示は確認できました。ただ、もう一つ対応が必要でした。

トップページは問題なく表示されます。しかし、決済完了後に遷移する `/success` のようなURLに直接アクセスしたり、ページをリロードしたりすると、404エラーが出ます。

なぜこうなるのか。

このアプリは **SPA（シングルページアプリケーション）** という構成で作られています。SPAでは、サーバーに実体として存在するファイルは基本的に `index.html` 一本です。`/` から `/success` への画面の切り替えは、JavaScriptがブラウザ上で処理しています。

問題は、ブラウザのアドレスバーに直接URLを入力したとき（またはリロードしたとき）です。このとき、ブラウザはサーバーに「`/success` というパスのファイルをください」とリクエストを送ります。サーバーはそのパスにファイルを探しますが、実体ファイルは存在しないので「ない」と応答します——これが404です。

解決策はシンプルで、「どんなパスへのリクエストも、すべて `index.html` に流す」というリダイレクトルールを設定することです。あとはJavaScriptが適切な画面を表示してくれます。

`netlify.toml` に `[[redirects]]` の設定を追記しました：

```toml
[build]
  command = "npm run build"
  publish = "dist"

[[redirects]]
  from = "/*"
  to = "/index.html"
  status = 200
```

一点、混同しやすいポイントを補足しておきます。Netlifyでこの設定を書く方法は2つあります。`netlify.toml` に書く方法と、`public/_redirects` というファイルに書く方法です。どちらも同じ効果がありますが、今回はビルド設定をまとめて管理している `netlify.toml` の中に書きました。

## Netlifyのクレジット制と向き合う

Netlifyの無料プランは「クレジット制」です。

無料プランには月ごとの利用枠（クレジット）があり、本番環境（mainブランチ）へのデプロイを行うたびに一定量を消費します。細かい修正のたびにmainへマージしていると、あっという間に枠を使い切ってしまいます。枠が尽きるとその月はそれ以上デプロイできなくなり、翌月まで待つことになります。

これを防ぐため、デプロイの運用を変えました。

Netlifyにはブランチへのpushに対してプレビューURLを発行する機能があります。作業ブランチで変更を加えたらまずプレビューで動作を確認し、確認が取れたものをまとめてmainにマージする、という流れです。本番デプロイの回数を絞ることで、クレジットを計画的に使う運用にしています。

## GA4でPV計測の土台を作る

Netlify移行後ほどなくして、GA4（Google Analytics 4）を導入しました。

課金を再開する基準を「月400PV」と決めていたのに、そもそもPVを計測する仕組みがありませんでした。何人来ているかわからないままでは、400PV達成の判断もできません。

導入の作業自体はシンプルです。GA4のトラッキングコード（数行のJavaScriptタグ）を `index.html` に追加するだけです。この作業はClaude Codeに依頼しました。

補足を一つ。このアプリはSPAなので、画面の切り替え（たとえば診断フォームから結果画面への遷移）を厳密な「ページビュー」として計測するには、別途設定が必要です。今回は「サイトに訪れた人数の大まかな把握」ができれば十分と判断し、基本のトラッキングタグの設置にとどめています。

ところで、冒頭で触れた「月400PV」という数字はなぜ400なのか。課金を本格的に動かし始めると、運用上どうしても月々の固定費が発生します。その固定費をまかなえる収益が出る水準になってから課金を有効にしたい——というのが考え方の起点です。客単価は¥300。訪問者のうち実際に課金してくれる割合は実績ゼロの段階では見積もりでしかありませんが、仮に0.5%程度と置いて逆算すると、月400PV前後という目安が出ました。思いつきの数字ではなく、客単価と課金率から逆算して決めた基準として持つようにしています。

## 課金を一旦オフにする：VITE_ENABLE_PAYMENT フラグ

移行が完了した時点で、課金導線を一旦オフにすることにしました。

誰にも知らせていない段階で課金を有効にしても意味がありません。PVがゼロなら、課金フローが実際に動くかどうかを確認する機会もない。まず人を集めることが先です。

そこで `VITE_ENABLE_PAYMENT` という環境変数フラグを導入しました。

- `false` のとき：決済ボタンを非表示にし、相性診断の解説を全文表示する（課金なしで読める状態）
- `true` のとき：決済ボタンを表示し、解説文の詳細をぼかして課金を促す（本来の課金導線）

切り替えはNetlifyの環境変数を書き換えるだけです。コードの変更もデプロイも不要です。月400PVを達成したと判断したタイミングで `true` に変更すれば、課金導線が復活します。

現時点では `false` に設定しています。

## 決済まわりは「宿題」として残した

課金を実際に再開するときには、決済まわりをNetlify向けに作り込む作業が必要です。サーバーサイドの処理を整えることや、一連の決済フローの動作検証は、課金を本格的に再開するタイミングでまとめて行う宿題として残しています。

現状は `VITE_ENABLE_PAYMENT=false` で決済導線自体をオフにしているため、実害はありません。ただし、課金を再開する前には、この宿題を片付ける必要があります。

## まとめ：回り道は多かったが、固定費は守れた

#8と#9を通して、回り道が多かったと感じます。

課金実装を進めてから商用利用の制約に気づき、移行先を探し、移行したら白画面トラブルが発生し、リダイレクト設定をしながら決済まわりの宿題も積み上がった。それでも最終的には、固定費を一切増やさずに立て直しを終えました。

「収益が見えてからコストをかける」という原則は、今回も守れました。

反省が一つあります。**使うサービスの商用利用ポリシーは、実装を始める前に確認すべきでした。** VercelのHobbyプランの規約を確認したのは、課金実装が終わった後でした。順番が逆です。実装コストをかけてから「使えない」と気づくのは、時間の無駄です。次に新しいサービスを使うときは、最初にポリシーを確認することを習慣にします。

それでも、#8と#9を振り返って素直に思うのは、この短い期間でここまで作ってリリースまで持っていけたことへの驚きです。AIを使わずに一人でやっていたら、同じボリュームを仕上げるには数ヶ月はかかっていたと思います。途中で熱が冷めて、そのままお蔵入りになっていた可能性の方が高い。今回が初めてのAI開発でしたが、AIと一緒に作る体験は、個人的にiPhoneが登場したときと同じくらいの衝撃がありました。時代が大きく変わったと、肌で感じています。

と同時に、「プログラムを書ける」だけでは生き残れない時代が来るかもしれない、という危機感もあります。取締役エンジニアとして、それは他人事ではありません。これからのエンジニアにとって重要なのは、AIとどう共存するか——そこに尽きると思っています。
