## はじめに

占いアプリ「HoroAi」を、Claude Codeを使って副業で開発している。

目標は月400PV。そのために、診断結果をSNSでシェアしてもらう機能を作った。

作りながら一番悩んだのは、技術そのものより設計判断だった。**画像を配るのか、リンクを配るのか。結果を再現するのにDBは要るのか。生年月日をどこまで守るのか。**

結論から書くと、DBもサーバー処理も使わずに、シェアされたリンクから診断結果を完全に再現できるようにした。しかも、生年月日はシェア画像にもURLにも1文字も含まれない。

その設計の話を書く。

---

## 1. 画像かリンクか、という最初の分岐

シェア機能を作るとき、最初に決めるべきはこれだった。

**画像を配る**なら、SNSのタイムラインで目を引く。でも、見た人はそこで終わる。アプリには来ない。

**リンクを配る**なら、踏んでもらえればアプリに来る。でも、タイムラインでは地味で埋もれる。

集客が目的なので、本当は両方欲しい。ただ、Web Share APIで画像とテキストを同時に渡しても、受け取るアプリ側がどちらを優先するかは実装依存で、確実に両方届く保証はない。

そこで、**複数の経路で冗長に届ける**方針にした。

- `navigator.share` に画像とテキスト（URL入り）の両方を渡す
- それとは別に「結果を見るリンクをコピー」ボタンを常設する
- シェア画像の中にもURLを焼き込んでおく

1回のシェアで全部届く保証はないが、どれか1つは届く。実際にLINEに送ってみると、画像とURL付きテキストの両方が並んで届いた。

![LINEに送ったシェア。画像・URL付きテキスト・リンクプレビューカードが並んでいる](/images/share-on-line.jpg)
*LINEに送ると、画像・URL付きテキスト・リンクプレビューの3つが届いた。*

## 2. シェア画像をCanvasで生成する

シェア画像は1080×1080の正方形。Canvas APIで動的に生成している。

![HoroAiのシェア画像。スコア・相性ラベル・星座・説明文が配置されている](/images/share-image-sample.jpg)
*Canvasで生成したシェア画像。すべての要素をプログラムで描画している。*

描いているのは、ロゴ・スコア・スコアラベル・星座ペア・説明文・フッターURL、そして背景の星空。全部プログラムで座標を指定して描いている。

出力はこう。

```ts
canvas.toBlob((blob) => resolve(blob), 'image/jpeg', 0.9);
```

### ハマりどころ1：フォントの読み込み待ち

最初、実機で生成した画像の日本語が化けた。

Canvasに文字を描くとき、Webフォントの読み込みが終わっていないと、フォールバックフォントで描画されてしまう。PCでは一瞬で読み込まれるので気づかないが、モバイル回線だと間に合わない。

対策はシンプルで、描画の前に待つ。

```ts
await document.fonts.ready;
```

これを関数の冒頭に入れるだけで解決した。

### ハマりどころ2：iOSが星座記号を絵文字にする

星座記号（♈ ♉ …）を `fillText` で描くと、iOSではカラー絵文字になってしまう。しかも、字形の送り幅が変わるせいで、中央揃えの計算までズレる。

これは根が深い問題で、[別記事](https://zenn.dev/kaminotk4/articles/ios-emoji-glyph)に詳しく書いた。結論だけ言うと、**フォント機構を使わず、SVGパスを `Path2D` で直接描く**ことで解決した。

```ts
ctx.fill(new Path2D(d));
```

画面側で使っているSVGアイコンのパスデータを、Canvas側からも同じものを参照している。画面と画像で見た目が揃うという副産物もあった。

## 3. 本題：DBを使わずに結果を再現する

ここからが本題だ。

シェアされたリンクを踏んだ人が、**生年月日を入力せずに、いきなり診断結果を見られる**ようにしたかった。リンクを踏んだ先で「まず2人分の生年月日を入力してください」と言われたら、その時点で離脱される。

普通に考えると、こうなる。

1. 診断結果をDBに保存する
2. 保存したレコードのIDをURLに載せる（`/result/abc123`）
3. リンクを踏まれたら、IDで引いて結果を表示する

これだとDBが要る。サーバー処理も要る。個人開発でコストをかけたくないし、そもそもDBの構築はまだ先送りしていたタスクだった。

### 気づき：スコアは「星座の組み合わせ」だけで決まっていた

ここで、自分のアプリのロジックを改めて確認してみた。

スコアを計算している関数は、生年月日（`BirthData`）を受け取っている。でも、その中で何をしているか。

- 生年月日から天体の正確な位置（黄経度数）を計算する
- **そこから「どの星座に入るか」だけを取り出す**
- 星座を火・地・風・水の4エレメントに変換する
- エレメントの組み合わせでスコアを決める

つまり、**度数は「どの星座か」を求めるためだけに使われていて、最終的なスコアには一切影響していなかった**。説明文の取得も、星座名をキーにして辞書を引いているだけだった。

ということは、**星座の組み合わせさえ分かれば、生年月日がなくても同じ結果を完全に再現できる**。

### 実装：スコア計算を「星座だけ」で動く形に切り出す

既存の関数は生年月日を受け取る形だったので、星座だけを受け取る純粋関数を切り出した。

```ts
// 新設：星座の組み合わせだけでスコアを計算する
function calculateScoreFromSigns(
  type: CompatibilityType,
  signs1: SignsByPlanet,
  signs2: SignsByPlanet,
): number

// 既存関数は、これを呼ぶだけの薄いラッパーにする
function calculateCompatibilityScore(type, person1, person2): number {
  const pos1 = calcPositions(person1);
  const pos2 = calcPositions(person2);
  return calculateScoreFromSigns(type, toSignsByPlanet(pos1), toSignsByPlanet(pos2));
}
```

既存の呼び出し元を壊さずに、新しい入口だけ増やす形だ。

重要なのは、`SignsByPlanet` という型が**度数を持てない**ことだ。

```ts
type SignsByPlanet = Partial<Record<Planet, ZodiacSign>>;
```

惑星から星座へのマップでしかない。度数を含む `PlanetPosition` から変換する時点で、度数は捨てられる。つまり、**この経路には度数が流れ込む余地が構造的にない**。

### URLに載せるのは、星座名だけ

あとは、星座の組み合わせをURLパラメータにするだけだ。

```
https://horoai.netlify.app/s?ct=love&p1su=libra&p2su=pisces&p1mo=sagittarius&p2mo=virgo&p1ve=scorpio&p2ve=aquarius
```

- `ct` … 相性のタイプ（love / friend / work）
- `p1su` … 1人目の太陽星座、`p2su` … 2人目の太陽星座
- 以下、月（mo）・水星（me）・金星（ve）・火星（ma）

惑星のコードは、タイプによらず共通にした。恋愛は太陽・月・金星、友達は太陽・月・水星、仕事は太陽・水星・火星と、使う惑星が違うが、コード体系を共通にしておけば、パースする側がシンプルになる。

このURLを踏むと、アプリはパラメータから星座を読み取り、その場でスコアと説明文を計算して、結果画面をそのまま表示する。**DBもサーバー処理も一切使っていない。**

### 壊れたURLへの備え

URLは書き換えられる。パラメータが足りないことも、値が不正なこともある。

パース関数は、例外を投げずに `null` を返す設計にした。

```ts
function parseShareParams(search: string): ParsedShareParams | null
```

タイプが `love / friend / work` のいずれでもなければ `null`。星座名が12星座のどれでもなければ `null`。呼び出し側は `null` を受け取ったら、何事もなかったように通常のトップ画面を表示する。

壊れたURLを踏んでもエラー画面にはならず、普通にアプリが開く。

## 4. 生年月日を、どこにも出さない

このアプリが扱うのは生年月日という個人情報だ。しかも、シェア機能は「他人に見せる」機能なので、ここを雑にすると事故になる。

方針は明快で、**シェアされるものに生年月日を一切含めない**。

前章で書いた通り、スコアも説明文も星座の組み合わせだけで決まる。だから、そもそも生年月日を渡す必要がない。あとは「うっかり渡してしまう」ことをどう防ぐか、という話になる。

### 型で封じる

シェア画像を生成する関数が受け取るパラメータには、生年月日を表す型（`BirthData` や `Date`）のフィールドを一切定義していない。

```ts
interface ShareImageParams {
  compatType: CompatibilityType;
  resultSymbols: string;
  score: number;
  scoreLabel: string;
  description: string;
  sign1: { sign: ZodiacSign; nameJa: string };
  sign2: { sign: ZodiacSign; nameJa: string };
}
```

渡せるのは星座と和名だけ。将来、誰かがうっかり生年月日を渡そうとしても、**型定義を書き換えない限りコンパイルが通らない**。ファイル冒頭にも「生年月日は意図的に受け取らない」とコメントを残した。

シェアURLの方も同じで、パラメータに載るのは星座名だけだ。実際に生成されるURLを見れば、日付らしき文字列がどこにもないことが分かる。

### 画面表示も、DOMごと出さない

シェアURLから開いたときの結果画面には、そもそも生年月日のデータが渡ってきていない。

結果画面のコンポーネントは、2つのモードを持つユニオン型にした。

```ts
type Props =
  | { mode: 'birthData'; person1: BirthData; person2: BirthData; ... }
  | { mode: 'signs'; signs1: SignsByPlanet; signs2: SignsByPlanet; ... };
```

通常フロー（自分で生年月日を入力した人）は `birthData` モードで、画面上部に「1990年5月10日生まれ × 1988年3月2日生まれ」と表示される。

シェアURLから来た人は `signs` モードで、この行は表示されない。CSSで隠しているのではなく、**JSXの条件分岐でDOM自体が生成されない**。

```tsx
{props.mode === 'birthData' && (
  <div className="compat-result-pair">…生年月日…</div>
)}
```

隠すのではなく、最初から存在しない。ページのソースを見ても、何も出てこない。

## 5. 細かいけれど効くところ

### キャンセルはエラーではない

`navigator.share` は、ユーザーが共有シートを閉じると `AbortError` を投げる。これをそのままエラー処理に流すと、「シェアに失敗しました」という表示が出てしまう。

でも、ユーザーは失敗していない。ただ気が変わっただけだ。

```ts
if (err instanceof DOMException && err.name === 'AbortError') {
  // ユーザーが共有シートを閉じただけ。エラー表示はしない
  setShareState('idle');
  return;
}
```

静かに元の状態に戻すだけにした。

### Web Share API非対応の環境

PCのブラウザなど、`navigator.share` が使えない環境もある。その場合は、生成した画像をダウンロードできるリンクを出す。

加えて、「結果を見るリンクをコピー」ボタンは、**対応・非対応にかかわらず常に表示**している。共有シート経由でURLがうまく渡らなかったときの保険であり、PCユーザーがリンクだけ欲しいときの導線でもある。

### OGP

シェアされたURLがSNSでカードとして展開されるよう、OGPタグも設定した。タイトル・説明・画像・URL・サイト名・タイプの6つと、`twitter:card` を `summary_large_image` に。

LINEに送ると、画像とテキストに加えて、リンクのプレビューカードも展開された。

## まとめ

やったことをまとめると、こうなる。

- Canvas APIでシェア画像を生成する（フォント読み込み待ちを忘れずに）
- Web Share APIで画像とURLを渡し、届かない環境向けに保険の導線も置く
- **スコアが星座の組み合わせだけで決まることに気づき、URLパラメータだけで結果を再現できるようにした。DBもサーバー処理も不要**
- 生年月日は、型・URL・DOMのすべてのレベルで、そもそも渡らない構造にした

一番の収穫は、**「DBが必要だ」と思い込んでいたものが、ロジックを見直したら不要だった**ことだ。

最初は「結果を保存してIDで引く」以外の方法が思い浮かばなかった。でも、自分のアプリが何を使って計算しているのかを冷静に確認したら、度数は最終結果に効いていなかった。必要な情報は12星座×惑星の組み合わせだけで、それはURLに載る程度の情報量だった。

作る前に、自分のロジックの実態を確認する。それだけで、DBもサーバーも要らなくなることがある。
