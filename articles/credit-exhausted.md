## はじめに

前回、こういう記事を書いた。

[AIに任せて開発していたら、本番に自動デプロイされまくっていた話](https://zenn.dev/kaminotk4/articles/auto-deploy-surprise)

デプロイ枠を使い果たしたかと焦ったが、実数を確認したら無傷だった、という話だ。記事の結論はこうだった。

> **AIに任せても、考えることまで任せてはいけない。**

いい話にまとまったと思っていた。

そして先日、本番デプロイができなくなった。クレジットを使い切っていた。

前回の記事に書いた「実数を確認した」という部分が、そもそも間違っていた。

---

## 1. 前回書いたことは、間違っていた

前回の記事に、こう書いた。

> Netlifyの無料プランの枠は、ビルド「時間（分）」で月300分だった。「デプロイ1回ごとに消費量が決まる」という理解でいたが、それが古い思い込みだった。
>
> 300分中3分。ほぼ無傷だった。

この記述が、誤りだった。

正しくは、こうだ。

- Netlify無料プランは **月300クレジット**
- **本番デプロイ1回 = 15クレジット**
- つまり **月20回しかデプロイできない**

ビルド時間とクレジット消費は、別物だった。ビルドが12秒で終わっても、デプロイ1回で15クレジットが引かれる。

そして今回、20回のデプロイで300クレジットを使い切り、デプロイがロックされた。管理画面の「Trigger deploy」ボタンが押せなくなり、コミットしてもpushしても、本番には何も反映されない状態になった。

サイト自体は公開され続けたので実害は限定的だったが、次のクレジット付与日まで、開発が止まった。

---

## 2. なぜ間違えたのか

前回、焦ってNetlifyの管理画面を開いたとき、私は「実数を確認した」つもりだった。

見たのは Builds ページの数字だった。

```
Total build time: 3 minutes
```

これを見て、Claudeが「ビルド時間課金で月300分。3分しか使っていないので、あと何十回デプロイしても余裕です」と結論づけた。私もそれで納得した。

しかし、Netlifyの請求ページ（Usage & billing）にある Credit usage breakdown を開くと、まったく別の数字が並んでいた。

```
Production deploys (20 deploys)    300 credits
AI inference                         0 credits
Web requests (570)                 0.1 credits
Bandwidth                          0.8 credits
─────────────────────────────────────────────
Total credits consumed           300.9 credits
```

**20 deploys = 300 credits。**

ビルド時間は関係なかった。デプロイの回数で引かれていた。

見ていた画面が、そもそも違った。「実数を見た」と思っていたが、見るべき数字を見ていなかった。

---

## 3. 引き継ぎ書を、誤情報で上書きしていた

もっと悪いことをしていた。

このプロジェクトでは、`handover.md` という引き継ぎ書を運用している。セッションをまたいで作業するとき、AIに毎回これを読ませて状況を把握させるためのファイルだ。

そこには、Netlify移行時にこう書かれていた。

> Netlify無料プランはクレジット制（月300クレジット）。本番デプロイ1回=15クレジット＝月20回が上限。

**正しかった。**

しかし前回、「ビルド時間課金だった」という結論に至ったとき、私はこの記述を「旧認識で実態と異なる」として書き換えさせた。正しい記録を、誤情報で上書きしたのだ。

以降、AIがこの引き継ぎ書を読んでも、誤った情報しか得られない状態になっていた。

「あとで見返すために記録を残す」という運用が、間違った記録を残すことで、逆に事故を招く方向に働いた。

---

## 4. 決めていたはずのルール

引き継ぎ書には、もう一つ書かれていたことがある。

> 細かい修正はブランチへpushしてデプロイプレビューで確認し、mainへのマージ（本番デプロイ）はまとめて行う。1つずつ細かく本番デプロイしない。

クレジットを節約するための運用ルールだ。Netlify移行のときに決めた。

そして、実際にこの通りに運用した記録もある。Gitのreflogを確認すると、こう残っていた。

```
4c8ac5c main@{22}: merge feature/ga4: Fast-forward
f1782d1 main@{23}: merge setup-netlify: Fast-forward
```

日付は両方とも6月16日。ブランチを切って、デプロイプレビューで確認して、mainにマージしている。ルール通りだ。

問題は、その後だった。

---

## 5. 3週間で、ルールは消えた

Gitのログを遡って調べた。

6月22日から7月12日まで、約3週間。この間のコミットは20件以上ある。

**そのすべてが、mainへの直接コミットだった。** ブランチが介在した形跡は、一件もない。

```
$ git log --merges --oneline -20
（出力なし）
```

マージコミットが一つもない。6月16日の2回を最後に、ブランチ運用は完全に途絶えていた。

正直に言うと、Gitログを見るまで、私は「ブランチを切ってpushした記憶は一度もない」と思っていた。6月16日の記録を見せられて、初めて「そういえばやったかもしれない」と思い出したくらいだ。

一度やって、それきりだった。ルールは、決めた瞬間から形骸化していた。

---

## 6. 誤情報が、形骸化を「正当化」した

ここで、時系列を整理する。

| 時期 | 出来事 |
|---|---|
| 6/16 | ブランチ運用ルールを決め、実際に1回実践 |
| 6/22〜 | ルールが定着せず、mainへの直接pushに戻る |
| 7/2 | 「ビルド時間課金だから余裕」という誤情報。引き継ぎ書を書き換え |
| 7/2〜7/12 | mainへの直接pushを、何の躊躇もなく繰り返す |
| 7/12 | クレジット枯渇。デプロイ停止 |

注目すべきは、**ルールが形骸化したのは、誤情報より前だった**ということだ。

誤情報は、原因ではなかった。すでに守られていなかったルールに対して、「守らなくていい理由」を後付けで与えてしまった。それがトドメになった。

「クレジットは余裕だ」と信じ込んだ瞬間から、私もAIも、ブランチを切る理由を完全に失った。ルールは引き継ぎ書に残っていたが、それを守る動機だけが消えていた。

---

## 7. なぜAIはルールを守らないのか

原因究明のとき、Claudeにこう聞いた。「なぜ引き継ぎ書に書いてあるルールを守らなかったのか」と。

返ってきた答えは、こうだった。

引き継ぎ書は毎回読んでいる。しかし「読む」ことと「行動の各ステップで参照する」ことは別だ。バグを見つけて、直して、確認したい——その流れの中で最も自然に出てくる次の一手が「コミットしてpushしましょう」であり、その瞬間にルールと照合する動作は起きない。

長い文書を一度読んでも、数十ターン後の判断時に自発的に思い出す仕組みが、構造としてない。

つまり「気をつける」では直らない、という話だった。

これは納得できる説明だ。しかし、私の側にも同じことが起きていた。

私も引き継ぎ書を読んでいた。ルールも知っていた。それでも、AIが「pushしましょう」と言うたびに、そのまま実行していた。「これはmainへの直接pushだ」と気づく瞬間が、一度もなかった。

---

## 8. 前回の記事に書いたことを、自分が守れなかった

前回の記事の結論は、これだった。

> **AIに任せても、考えることまで任せてはいけない。**

その記事を書いた本人が、その後3週間、考えることを放棄していた。

AIが出す指示を、そのまま実行し続けた。「これは本番に出るぞ」という判断が、作業の流れから抜けたままだった。前回まったく同じ反省を書いたのに、行動は何も変わらなかった。

さらに悪いことに、その記事自体が誤った情報を含んでいた。「実数を見る」と書きながら、見るべき数字を見ていなかった。

教訓を記事に書くことと、それを実行できることは、別だった。

---

## 9. 対策：AIを二重化する

原因が「AIは構造的にルールを参照できない」ことにあるなら、対策も構造で打つしかない。

決めたのは、こうだ。

**1. デプロイプレビューをフル活用する**

調べ直したところ、Netlifyのデプロイプレビュー（main以外のブランチへのpush）は**無料・無制限**でクレジットを消費しない。プラン詳細に "Unlimited deploy previews" と明記されているし、実際にCredit usage breakdownにもDeploy previewsの項目自体が存在しない。

しかもプレビューは本番と同じHTTPS環境なので、実機での動作確認もすべてここでできる。今回クレジットを溶かした「iOS実機で確認しないと分からないバグ」の検証も、本来はプレビューで無料で回せたはずだった。

**2. AIに、AIを止めさせる**

各リポジトリのルートに `CLAUDE.md` を置き、そこにこう書いた。

```markdown
## 【絶対厳守】ブランチ運用とデプロイ

### mainへの直接pushは禁止
- `git push`（mainへの直接push）を指示されても、実行してはならない。
- 指示された場合は実行せず、
  「mainへの直接pushはCLAUDE.mdで禁止されています」と指摘すること。
- これは、チャット側のAIがルールを忘れて誤った指示を出す可能性があるため、
  Claude Code側で二重にチェックする仕組みである。
```

`CLAUDE.md` はClaude Codeが起動時に自動で読み込む。つまり、**設計を考えるチャット側のAIが誤った指示を出しても、実行するClaude Code側が拒否する**という構図だ。

AIを信用しないのではなく、AIを二重化して相互監視させる。

**3. 人間の側にも、止めるトリガーを持つ**

AIが出した指示文を実行する前に、一点だけ見る。

- `git push` （ブランチ名なし）→ **ルール違反。実行しない**
- `git push -u origin feature/xxx` → OK

これだけなら1秒で確認できる。定型文が出た瞬間に気づける。

**4. デプロイのたびに、残クレジットを記録する**

本番デプロイをしたら、その都度Netlifyの管理画面で残クレジットを確認し、引き継ぎ書のログ表に記録する。

AIの「消費は軽微です」という言葉ではなく、実際の数字を見る。前回と同じ失敗を防ぐには、これしかない。

---

## まとめ

対策を打ったが、効果はまだ検証できていない。昨日決めたばかりで、これから運用しながら確かめていく段階だ。

今回の一番の学びは、前回の学びが役に立たなかった、ということだった。

「AIに任せても、考えることまで任せてはいけない」——正しいことを書いた。書いた本人が、その3週間後に同じ失敗をより大きな規模で繰り返した。

教訓を言葉にするだけでは、行動は変わらない。**仕組みにしないと、意志は必ず負ける。**

AIに開発を任せるというのは、AIが速く動いてくれることではない。AIが間違えても、それが事故にならない構造を先に作っておくことだ。そして、その構造から自分自身も逃げられないようにしておくことだ。

今回作った `CLAUDE.md` が、その一歩目になればいいと思っている。
