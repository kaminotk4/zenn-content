## ¥300の課金機能を作ろうとした

相性占いは「スコアは無料・詳しい解説は¥300」という設計で作っていました（[第4回の設計記事](https://zenn.dev/kaminotk4/articles/design-horoscope-app)参照）。

画面はできている。詳しい解説文も432パターン揃っている。あとは「¥300払ったら全文が読める」という仕組みを作るだけです。

決済にはStripeを使うと最初から決めていました。国内でも実績が多く、クレジットカードのほかPayPayにも対応できる。週5時間の副業でゼロから決済を自前実装するのは時間の無駄です。Stripeに乗っかる一択でした。

問題は、**Stripeをどの方式で実装するか**です。

---

## Stripe Payment LinksかCheckoutか

Stripeで課金を実装するとき、選択肢の筆頭として2つの方式が出てきました。

| 方式 | 概要 |
|---|---|
| **Payment Links** | Stripeの管理画面でURLを発行して、そこにユーザーを誘導するだけ。コード不要 |
| **Stripe Checkout** | サーバー側でセッションを作成してStripeの決済画面にリダイレクトさせる。コードが必要 |

Payment Linksは圧倒的に手軽です。コードを書かなくてもURLを発行するだけで課金導線が作れます。

ただし、今回の用途では**致命的な問題**がありました。

Payment Linksはアプリと独立しています。ユーザーが決済を完了しても、「この人が今このアプリで相性占いをしているセッション」と紐づける手段がありません。結果として**「課金したのに相性占いの全文が表示されない」**という事故が起きやすくなります。

Stripe Checkoutなら、アプリ側でセッションを作成してから決済に誘導します。決済完了後にWebhookで通知が届くため、アプリ側で「誰がいつ課金したか」を把握できます。課金判定と全文表示の制御が確実にできます。

**Stripe Checkoutを選択しました。**

---

## サーバーサイドが必要になった

Stripe Checkoutには、ひとつ問題があります。

**サーバーサイドの処理が必要です。**

Checkoutのセッション作成にはStripeのシークレットキーを使います。名前の通り、外部に漏らしてはいけないキーです。フロントエンドのコードに書いてしまうと、ブラウザの開発者ツールで誰でも中身を見られます。シークレットキーが漏れると、第三者が自分のStripeアカウントを悪用できてしまいます。

つまり、「シークレットキーを安全に持てるサーバー側の処理」が必要です。

このアプリはReact + Vite + TypeScriptのフロントエンドのみで構成されていました。サーバーはありません。

そこで採用したのが **Vercel Functions** です。

### Vercel Functionsとは

Vercel（バーセル）は、フロントエンドのデプロイに使われるホスティングサービスです。GitHubリポジトリと連携して、pushするだけで自動デプロイができます。

その Vercel には **Functions** という機能があります。フロントエンドと同じリポジトリの `api/` フォルダにファイルを置くだけで、サーバーサイドのAPIエンドポイントが作れます。専用のサーバーを別途立てる必要がありません。

たとえば `api/create-checkout-session.ts` というファイルを作ると、`https://yourdomain.vercel.app/api/create-checkout-session` というエンドポイントが生まれます。このファイルの中でシークレットキーを使った処理を書けば、ブラウザからは中身が見えません。フロントエンドエンジニアがサーバーを意識せずにバックエンド処理を追加できる仕組みです。

## 実装：Vercelに開設して決済APIを作った

課金まわりの実装を始めるにあたり、まずVercelにアカウントを作成し、GitHubリポジトリと連携してアプリをデプロイしました。

次に `api/create-checkout-session.ts` を作成しました。フロントエンドから「相性占いの決済セッションを作ってください」というリクエストを受け取り、Stripeに対してCheckoutセッションを作成して、そのURLを返す処理です。

```typescript
import Stripe from 'stripe';

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!);

export default async function handler(req: any, res: any) {
  const session = await stripe.checkout.sessions.create({
    payment_method_types: ['card'],
    line_items: [{
      price_data: {
        currency: 'jpy',
        product_data: { name: '相性占い 詳細レポート' },
        unit_amount: 300,
      },
      quantity: 1,
    }],
    mode: 'payment',
    success_url: `${req.headers.origin}/success`,
    cancel_url: `${req.headers.origin}/`,
  });
  res.json({ url: session.url });
}
```

※上記は要点を抜き出した概略です。型定義やエラーハンドリング、リクエストメソッドのチェックなどは省略しています。

ただ、後から振り返ると、この実装は決済完了の検証という観点で甘さがありました。「決済画面から戻ってきたら完了扱い」という前提で作っており、本当に決済が成功したかをきちんと確かめる処理が入っていなかった。当時は動くことを確認して満足していたのですが、その甘さには後で気づくことになります。詳しくは #9 で触れます。

相性診断の結果画面（`CompatibilityResult.tsx`）にある「詳細を見る（¥300）」ボタンから、このAPIを呼び出す形で組み込みました。

> ボタンを押す → `/api/create-checkout-session` を呼ぶ → StripeのCheckout URLが返ってくる → Stripeの決済画面にリダイレクト

流れ自体はシンプルで、思ったよりあっけなく実装できました。自分ひとりでやっていたら、調査と試行錯誤でもっと時間がかかっていたと思います。Claude Codeの恩恵を実感した場面のひとつです。

## 転機：Vercel Hobbyプランは商用利用禁止だった

課金まわりの実装が一段落したころ、「このまま公開するなら、利用規約や免責事項をサイトに掲載しておくべきでは」と気づきました。その準備を進める中で、ホスティング先であるVercel自体の規約も確認することになり——そこで発覚しました。

そこに明記されていました（意訳）。

> Vercel の Hobby プランは、非商用・個人目的のプロジェクト向けです。

課金を実装してお金を受け取る——これは明確に**商用利用**です。Hobbyプランのまま使い続けることはできません。

正直、かなりがっかりしました。Vercelを選ぶ段階で、なぜこの問題に気づけなかったのか。Claude Codeと一緒に実装を進める中で、技術的な判断の速さに慣れてしまっていたのかもしれません。AIは強力ですが、利用規約の含意まで自動で拾ってくれるわけではない——最終的なチェックは人間がやる必要がある、ということを実感しました。そして、もし「規約を載せるべきでは」と自分で気づいていなければ、このまま課金機能を公開していた可能性もある。その怖さは今も少し残っています。

選択肢は2つです。

**① Vercel Proにアップグレードする**（月$20〜）

商用利用が許可されます。ただし、アプリはまだリリース前。PVも売上もゼロの段階で、ホスティングだけ月3,000円が先行します。

**② 別のホスティングサービスに移行する**

商用利用を無料プランで許可しているサービスに乗り換える。移行の手間はかかりますが、固定費は増えません。

「収益が出る前に固定費を増やすのは避けたい」——その判断は一貫していました。占いサイトに需要があるかどうか、どれくらいの人に使ってもらえるかは、この時点ではまだ何もわかっていません。誰にも知られていないサービスのために固定費が毎月出続けるのは、事業として筋が悪い。「見込みが見えてからコストをかける」というのは、副業だろうと本業だろうと変わらない原則だと思っています。

**移行する方向で検討することにしました。**

どのサービスに移るか。その選定と移行作業、そして最終的に課金を一旦オフにする判断までの話は、次回（#9）に続きます。
